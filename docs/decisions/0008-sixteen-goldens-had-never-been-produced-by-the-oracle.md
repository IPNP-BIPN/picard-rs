# 0008. Sixteen goldens had never been produced by the oracle

**Status:** accepted
**Date:** 2026-07-29

## What was found

The repository's bit-identity contract says goldens come from the pinned reference running in a
digest-pinned `linux/amd64` container on JDK 17, on real x86-64 CI. Moving the conformance suites
into `tools/conformance/manifest.json` required enumerating which CI step regenerates which golden,
and the enumeration came up short:

| | goldens |
|---|---:|
| committed under `crates/picard-analysis/tests/data` | 57 |
| regenerated by a CI step and compared against the oracle | 41 |
| **never regenerated by anything** | **16** |

The sixteen were compared only by the Rust tests, against the committed copy. A Rust test that
reads a golden nothing re-derives is asserting that the port reproduces a file of unknown
provenance, which is a strictly weaker claim than the one the README makes, and nothing in the
repository distinguished the two categories.

## The provenance is recoverable, and it is not the oracle

Nine of the sixteen carry absolute paths of the form

```
UR:file:///var/folders/jj/v73y0qn92zzdyz0prxb5ywb40000gn/T/b2i6199996068216553390/in.fasta
```

`/var/folders/<...>/T/` is the macOS per-user temporary directory. The oracle is a Linux container;
a run inside it writes `/tmp/...`. So those nine were produced by a JVM on the maintainer's
machine, not by the pinned image, and the harnesses confirm how the path got there: they build
their fixtures with `Files.createTempDirectory`, and Picard copies the fixture's URI into the
`@SQ UR:` field of everything it writes.

Affected: `bed_to_interval_list`, `interval_list_to_bed`, `interval_list_tools` (and its `setops`
and `invert` corpora), `liftover_interval_list`, `extract_sequences`, `scatter_intervals_by_ns`,
`merge_bam_alignment_full`. The in-flight `interval_list_tools_padbreak` corpus has the same
signature.

The remaining seven (`quality_score_distribution`, `gc_bias`, `accumulate_quality_yield`,
`non_n_fasta_size`, `normalize_fasta`, `sam_to_fastq_with_tags`, `merge_bam_alignment`) carry no
path, so their origin cannot be read off the bytes. Not being disprovable is not the same as being
oracle-backed, and they are treated the same way.

## Four oracle-backed goldens also carry macOS paths, and that is fine

`rnaseq_metrics`, `snvq`, `downsample_sam` and `create_sequence_dictionary` were committed from the
same machine, but each one's macOS path sits precisely in a field the suite canonicalizes away: the
`# <Tool>` header, the `@PG CL:`, the `UR:`. CI regenerates these files in the container on every
run and compares the canonicalized remainder, so the content the claim rests on is re-derived from
the oracle each time and the committed bytes are only a cache. The distinction that matters is not
where a file was authored but whether anything re-derives it.

## What was done

1. Every golden is declared in `tools/conformance/manifest.json` with a `status`: `oracle-backed`
   (41) or `unchecked` (16). The status is visible in the CI job name, so the weaker claim cannot
   be mistaken for the stronger one while reading a green run.
2. The sixteen now have generated CI suites of their own, so the next run is the first time they
   are compared against the oracle at all. Where the golden holds a per-run temp path, the suite
   declares `strip_ur` (and `strip_pg` for the tools that write a command line), with the reason
   recorded beside it: a path from `Files.createTempDirectory` can never recur, so it is not
   something a byte comparison can be asked to reproduce.
3. `tools/conformance/audit_goldens.py` fails the `guard` job if a committed golden belongs to no
   suite, so the condition cannot come back silently.

## What is deliberately left open

The first CI run of the sixteen may well be red, and a red result there is the point of the
exercise: it distinguishes "the golden was fine, only its paths were machine-specific" from "the
golden was never right". Until that run happens, none of the sixteen may be described as
byte-identical, and the affected tools are reported at the weaker claim.

The lesson generalizes past this repository: a conformance corpus is only as strong as the step
that re-derives it, and there was no mechanism making that step mandatory. There is one now.
