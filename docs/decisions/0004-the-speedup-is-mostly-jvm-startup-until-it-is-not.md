# 0004. The speedup is mostly JVM startup, until the input is big enough that it is not

**Status:** accepted; first throughput measurement, with its own correction attached
**Date:** 2026-07-21

## Why this exists

The program's plan is entirely about bit-identity and says nothing about speed. That is a real
gap: a byte-identical port that is slower than the original is a curiosity, and "how much faster"
is the first question anyone asks. This is the first measurement, and it comes with a correction
to itself, because the first number I produced was wrong in the flattering direction.

## Method

`CollectAlignmentSummaryMetrics` over a synthetic BAM generated by
`tools/benchmark/MakeBenchmarkBam.java`: a fixed-seed mixture of read lengths, mapping qualities,
strands, pairing states, indels, splices, soft and hard clips, no-calls and mismatches, so the
collector takes every branch rather than the cheapest one. A benchmark over a million identical
perfect reads measures branch prediction, not the tool.

**Both implementations run in the same container, on the same platform.** The Rust binary is
cross-built for `linux/amd64` and run inside the pinned oracle image, next to the JVM. Timing a
native arm64 binary against an emulated x86-64 JVM would have produced a large number and no
information.

Three runs each, median reported. Output compared byte for byte in the same session.

## The correction

At **200,000 reads** the first measurement said:

| | median |
|---|---:|
| Picard, GKL default | 2.45 s |
| Rust | 0.475 s |
| | **5.2x** |

At **2,000,000 reads**, the same code, the same machine:

| | median |
|---|---:|
| JVM startup floor (`--version`, no work) | 1.28 s |
| Picard, GKL default | 9.92 s |
| Picard, `USE_JDK_INFLATER=true` | 9.71 s |
| Rust | 4.90 s |
| **wall clock** | **2.0x** |
| **net of JVM startup** | **1.8x** |

**The 5.2x was mostly `java -jar`.** At 200,000 reads the JVM's ~1.3 s of startup is more than
half of Picard's 2.45 s, so the ratio was measuring process launch. At ten times the input it
falls to 2.0x and keeps falling toward the steady-state ratio.

Both numbers are real and they answer different questions. For a user running one tool on a small
file, the 5x is what they experience, because startup is a cost they pay. For anyone asking how
fast the port processes reads, only the large-input number means anything. A benchmark that does
not say which question it answers is choosing the flattering one by default.

## Where the time goes

`PICARD_RS_TIMING=1` on the 2M-read input:

| phase | seconds | share |
|---|---:|---:|
| read the file | 0.065 | 1% |
| BGZF decompress | 1.163 | 24% |
| read the reference | 0.002 | — |
| **decode records and collect** | **3.901** | **75%** |
| write the metrics | 0.003 | — |

Three quarters is the work itself: decoding records and running the collector. So the port is not
losing to I/O structure, and the remaining headroom is in the two places nothing has been done
yet — BGZF decompression is single-threaded, and record decoding allocates per record.

**No optimisation work has been done at all.** This number is a floor, not a ceiling, and it was
produced by code written to be byte-identical and readable.

## Context: riker

`fulcrumgenomics/riker` claims 12–38x over Picard for the same tools. That is not in tension with
2.0x; it is a different object. Riker does not target byte equivalence, which frees it to use a
leaner record model, and it is a mature optimisation effort where this is none. Its number and
this one should not be compared as though they measure the same thing.

What can be said is that byte-identity has a cost, that the cost has now been measured once
rather than assumed, and that the port is faster than the reference rather than slower — which
was not guaranteed and is the question this record exists to answer.

## Verification

Byte-identity is asserted in the same run that produces the timing, on both corpus sizes:

```
200,000 reads, byte-identical: True
2,000,000 reads, byte-identical: True
GKL vs JDK inflater identical: True
```

The last line confirms that the deflater choice pinned in the oracle contract does not change the
metrics, which the contract assumes and had not checked.

CI repeats the whole thing on **real x86-64**, where neither implementation is emulated, and
fails if the outputs stop matching. The timing there is the authoritative figure; the numbers
above are from an emulated container and are reported as such.
